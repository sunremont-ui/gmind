# Алгоритм раскладки узлов (node distribution)

Документация к движку раскладки Gmind: как узлы распределяются в пространстве,
как гарантируется отсутствие наложений, как включить логи и как безопасно
модифицировать алгоритм.

Код:
- [`frontend/src/renderer/layout.ts`](../frontend/src/renderer/layout.ts) — сам алгоритм
- [`frontend/src/renderer/layoutLog.ts`](../frontend/src/renderer/layoutLog.ts) — логирование/отладка
- [`frontend/src/renderer/layout.test.ts`](../frontend/src/renderer/layout.test.ts) — тесты (в т.ч. на отсутствие наложений)

---

## 1. Общая картина

Раскладка — чистая функция: дерево `Topic` → координаты `LayoutNode`.

```
Topic (данные)
   │ buildLayout()            меряем размер каждого узла (ширина по тексту, высота)
   ▼
LayoutNode (x=0,y=0,width,height,children)
   │ computeTreeLayout() → computeLayout()
   ▼
LayoutNode с координатами  +  { width, height } холста
```

`computeLayout` делает 5 шагов:

1. **`layoutRecursive(root)`** — пост-обход (post-order): сперва раскладываем
   детей, потом пакуем их вокруг родителя. Структура раскладки берётся
   **per-node** из `topic.structure_class` (см. §3).
2. **`postProcessFolded`** — у свёрнутых узлов дети схлопываются в точку родителя.
3. **`resolveOverlaps`** — глобальная страховка от наложений (§5).
4. **`collectBounds` + `shiftGlobal`** — сдвигаем всё в положительные координаты
   и считаем размер холста.
5. **`run.finish()`** — закрываем лог-прогон (§6).

## 2. Ключевая идея: упаковка по измеренным bbox

Раньше соседние поддеревья разносились по эвристике «высота поддерева»
(`subtreeHeight` = сумма высот детей). Это **ломалось на смешанных
направлениях**: если у одной ветки дети растут вниз (`tree-down`), её реальный
габарит шире и ниже, чем считала эвристика → соседняя ветка наезжала.

Сейчас перед упаковкой детей мы **измеряем реальный bounding box** каждого уже
разложенного поддерева:

```ts
function measureSubtree(n): BBox   // {minX,minY,maxX,maxY} по узлу + всем потомкам
```

Поскольку обход пост-порядковый, на момент упаковки потомки уже стоят на своих
местах, и `measureSubtree` даёт точный габарит — независимо от того, какие
направления у вложенных веток.

Два упаковщика покрывают все древовидные структуры:

- **`packVertical(side: 'left'|'right')`** — стопка поддеревьев сбоку (mindmap,
  `tree-left`, `tree-right`). Слот по **высоте** = реальный bbox; верх каждого
  поддерева ставится вплотную к низу предыдущего + `siblingGap`.
- **`packHorizontal(direction: 'up'|'down')`** — стопка сверху/снизу (`tree-up`,
  `tree-down`, `org-chart`). Слот по **ширине** = реальный bbox.

Так как соседи разнесены по непересекающимся полосам (вертикальным или
горизонтальным), **наложение между разными ветками одного родителя
математически невозможно**. Это проверяется тестами `no overlap …`.

`translate(node, dx, dy)` двигает узел **вместе с поддеревом** (в отличие от
`shiftSubtree`, который двигает только потомков).

### Per-child направление (`child_dir`)

`packDirectional` раскладывает детей с учётом **индивидуального** направления:
каждый ребёнок может иметь поле `topic.child_dir` (`up|down|left|right`). Дети
группируются по направлению, и каждая группа пакуется независимо
(`packVertical`/`packHorizontal`). Дети **без** `child_dir` идут в направлении
по умолчанию для структуры родителя (`defaultDir(structure_class, branch_side)`).

Так новый ребёнок встаёт в выбранную сторону, **а остальные дети остаются там,
где были** (раскладку родителя не меняем). Группы занимают разные
полуплоскости/квадранты; редкие угловые наложения добивает глобальный sweep.

`child_dir` хранится per-child и персистится (backend `model.Topic.ChildDir`,
JSON-блоб воркбука). Создаётся по якорю узла: **левый клик** по точке → ребёнок в
её сторону; **правый клик** → меню «Направление»; драг в пустоту → в сторону драга.
Всё сходится в `MindMap.createChildInDirection`.

> **Рендеринг рёбер/бейджей/fold — не здесь.** Этот файл только про
> распределение координат (`layout.ts`). Рисование рёбер (точки выхода по стороне
> ребёнка, толщина = размер поддерева, цвет = `edge_weight`), бейджи числа детей и
> per-side fold (`folded_sides`, скрытие без переракладки) живут в
> `renderer.tsx`. Floating-узлы раскладываются как отдельные корни поддерева
> (`MindMap.floatingLayouts`), используя тот же `computeTreeLayout`. Детали —
> `wiki/05-layout-engine.md` и `skills/layout-collision.md`.

## 3. Структуры раскладки (per-node)

`structure_class` задаётся на каждом узле и определяет, как раскладываются его
**дети**. Значение берётся в `getStructure()`: сперва `topic.structure_class`,
затем `topicStructureMap`, иначе `defaultStructure`.

| `structure_class`      | Упаковщик                | Куда растут дети |
|------------------------|--------------------------|------------------|
| `mindmap` (default)    | `packVertical(side)`     | вправо или влево (`branch_side`) |
| `tree-right` / `tree`  | `packVertical('right')`  | вправо |
| `tree-left`            | `packVertical('left')`   | влево |
| `tree-down` / `org-chart` | `packHorizontal('down')` | вниз |
| `tree-up`              | `packHorizontal('up')`   | вверх |
| `radial`               | `layoutRadial`           | по кругу (8 направлений) |
| `fishbone`             | `layoutFishbone`         | диагонали от «хребта» |

`radial` и `fishbone` пока используют старую эвристику `subtreeWidth/Height` и
разносят узлы по расстоянию — их подстраховывает глобальный sweep (§5).

> **Связь с UI:** клик/перетаскивание от якоря узла создаёт ребёнка «в
> направлении» — фактически проставляет `structure_class` родителя
> (`tree-up/right/down/left`) и добавляет дочерний узел. См.
> `MindMap.createChildInDirection`.

## 4. Параметры (gaps)

| Константа              | Значение | Что значит |
|------------------------|----------|------------|
| `DEFAULT_LEVEL_GAP`    | 100      | расстояние родитель→ребёнок (вдоль направления роста) |
| `DEFAULT_SIBLING_GAP`  | 24       | зазор между соседними поддеревьями |
| `DEFAULT_CHILD_GAP`    | 16       | добавка к level gap |

Переопределяются:
- глобально — через `gaps` в `computeTreeLayout`;
- per-node — через `topic.level_gap` / `topic.sibling_gap`.

## 5. Глобальный sweep от наложений (`resolveOverlaps`)

Страховка для случаев, которые упаковщики не покрывают (радиал, ёлочка,
экзотические смешения). Алгоритм:

1. Собрать **видимые** узлы (в свёрнутые поддеревья не спускаемся), запомнив
   порядок обхода (`enter`/`exit`) и размер поддерева — по ним определяется
   родство и кто кому уступает.
2. Разложить узлы по равномерной сетке (`SWEEP_CELL`, 160px): в пары попадают
   только соседи по ячейке, поэтому проход линеен по числу узлов и **работает
   на картах любого размера**. Ограничения `SWEEP_MAX_NODES` больше нет — до
   него карты крупнее 300 узлов оставались с наложениями.
3. До `SWEEP_PASSES` (6) проходов по парам-кандидатам:
   - если проникновение по обеим осям > `OVERLAP_EPSILON` (1px) — это наложение;
   - уступает: потомок (предка двигать нельзя — он утащит потомка за собой),
     иначе меньшее поддерево;
   - двигаем **целое поддерево** (`translate`), а не один узел: сдвиг листа
     оставлял его детей на месте и рвал ветку;
   - обычный случай — короткий толчок по оси наименьшего проникновения прочь
     от соседа; накопленный сдвиг узла запоминается;
   - если толчок разворачивает узел назад по его же накопленному сдвигу, значит
     он зажат между двумя соседями: вместо качелей вызывается `escapeAll` —
     уход одним сдвигом сразу от всех текущих соседей, из четырёх направлений
     выбирается самое короткое и не возвращающее назад.
4. Если за проход никто не сдвинулся — выходим раньше.

Параметры — константы вверху `layout.ts`: `OVERLAP_EPSILON`, `SWEEP_CELL`,
`SWEEP_PASSES`, `GROUP_CLEARANCE`.

Перед этим проходом группы направлений одного родителя разводит
`separateGroups` (§4): каждая группа при пересечении отодвигается **вдоль
своего направления**, уступает та, которой нужен меньший сдвиг.

## 6. Логи и отладка

Логирование по умолчанию **выключено** (нулевая стоимость). Включить:

```js
// в консоли браузера
gmindLayoutDebug(true)     // включить (сохраняется в localStorage)
gmindLayoutDebug(false)    // выключить
gmindLastLayout()          // stats последнего прогона (без включения логов)
```

или вручную: `localStorage['gmind.layoutDebug'] = '1'`.

При включённых логах каждый прогон печатает свёрнутую группу в консоль:

```
[layout] 42 nodes · 12 packs · overlaps 2/3 · 1.8ms
  pack     a1b2c3d4 pack 3 children as "mindmap/right"
  overlap  …        overlap e5f6 ↔ a7b8 {penX, penY}
  resolve  e5f6…    nudged by (0.0, -25.0)
  ...
```

Поля сводки: число узлов · число упаковок · `устранено/найдено` наложений ·
время. Типы событий: `pack`, `overlap`, `resolve`, `info`. Подробности —
`LayoutRun` в `layoutLog.ts`.

## 7. Как модифицировать

- **Новая структура раскладки:** добавьте `case` в `switch` внутри
  `layoutRecursive`, напишите упаковщик (по образцу `packVertical` /
  `packHorizontal`) и вызовите `run.pack(id, name, count)`. Если упаковка
  гарантирует непересечение полос — наложений не будет; иначе положитесь на
  sweep.
- **Изменить зазоры/плотность:** константы `DEFAULT_*_GAP` или per-node поля.
- **Тонкая настройка sweep:** `OVERLAP_EPSILON`, `SWEEP_CELL`, `SWEEP_PASSES`,
  `GROUP_CLEARANCE`.
- **Инвариант:** упаковщик в конце должен ставить `n.x = n.y = 0` (родитель в
  локальном начале координат); глобальный сдвиг сделает `shiftGlobal`.
- **Тесты:** проверки направления — в `layout.test.ts`; инварианты «нет
  наложений» (включая случайные и крупные карты) — в `layoutOverlap.test.ts`;
  бюджеты времени и линейность — в `layoutPerf.test.ts`.

## 8. Сложность

- `measureSubtree` суммарно по дереву — O(n·d), где d — глубина (на практике
  близко к O(n) для сбалансированных деревьев).
- Глобальный sweep — ≈O(n·passes) за счёт сетки; пары берутся только из общих
  ячеек, а не из всех сочетаний.
- Замер: карта в 3109 узлов раскладывается за ~13 мс без единого наложения;
  типовые карты (сотни узлов) — единицы миллисекунд (видно в логах).
