# Markdown как рабочий формат карты

Карта Gmind может быть представлением обычного `.md`-файла: открыть → править
как mindmap → сохранить обратно в тот же файл. Формат остаётся читаемым
человеком и другими редакторами (Obsidian, VS Code).

## Где что лежит

| Слой | Файл |
|---|---|
| Go парсер/рендерер | `backend/internal/markdown/markdown.go` (+ `markdown_test.go`) |
| Go HTTP-обвязка | `backend/internal/api/markdown_files.go` |
| Project file CRUD | `backend/internal/api/project_files.go` |
| TS парсер/рендерер | `frontend/src/utils/markdown.ts` (+ `markdown.test.ts`) |
| TS: Topic → Markdown | `frontend/src/utils/markdownExport.ts` |
| API-клиент | `frontend/src/api/markdown.ts` |
| UI | `frontend/src/components/MarkdownPanel/MarkdownPanel.tsx`, `modules/markdown/module.ts` |
| Корневое дерево | `frontend/src/components/Sidebar/ProjectTree.tsx`, `api/projects.ts` |

Обе реализации держат **паритет**: любое изменение формата правится в двух
местах, иначе карта, сохранённая бэкендом, разъедется с фронтендовым превью.

## Соответствие Markdown ↔ узел

| Markdown | Узел |
|---|---|
| `# / ## / ### …` | голова (`title`), `md_form: "heading"` |
| `- пункт`, `1. пункт` (вложенность = 2 пробела) | голова, `md_form: "list"` |
| абзацы под узлом | тело (`body`) — модель «голова + тело» |
| `> цитата` | `notes` |
| `<!-- gmind: {"shape":"hexagon","icon":"Star"} -->` | `shape`, `icon`, цвета, `memory_kind`, `masys_ref`, `markers`, `labels`, `progress`, `position`… |
| ```` ```code``` ```` | целиком уходит в тело, внутри ничего не разбирается |
| YAML-преамбула `--- … ---` | отбрасывается |

Уровень пункта списка = уровень последнего заголовка + 1 + отступ/2.
Глубже 6-го уровня заголовков в Markdown нет — дерево продолжается вложенными
списками.

## Инварианты (покрыты тестами с обеих сторон)

1. **Стабильность:** `Render(Parse(x))` не меняется на втором проходе.
2. **Форма узла не переписывается.** Списки остаются списками, заголовки —
   заголовками (`Topic.MdForm` / `md_form`). Узел, дописанный в приложении под
   пунктом списка, становится вложенным пунктом, а не заголовком посреди списка.
   Внутри списка заголовков быть не может — вся ветка идёт пунктами.
3. **Корень всегда заголовок** — файл, начинающийся с `- пункт`, читался бы как
   список без названия.
4. **Экранирование тела.** Строка тела, похожая на `- пункт` / `# заголовок` /
   `> цитату`, пишется с `\` — иначе при повторном открытии тело распалось бы
   на отдельные узлы. При разборе `\` снимается.
5. **Без лишних отбивок** — подряд идущие пустые строки схлопываются до одной.

## Эндпоинты

| Метод | Path | Назначение |
|---|---|---|
| GET | `/api/v1/md/files?dir=` | Обзор хранилища (каталоги + `.md`) |
| POST | `/api/v1/md/open` | `{path, reuse}` → открыть файл как карту, связать |
| POST | `/api/v1/workbooks/{id}/md/save` | `{path?, sheet_id?}` → записать в связанный файл или «Сохранить как» |
| POST | `/api/v1/workbooks/{id}/md/reload` | Перечитать файл (правки из другого редактора) |
| POST | `/api/v1/workbooks/import/markdown` | JSON `{content,title,path}` / multipart / raw `text/markdown` |
| GET | `/api/v1/workbooks/{id}/export/markdown` | Скачать `.md` |
| POST | `/api/v1/projects/files` | Создать `.md`/`.markdown` внутри открытого корня и пересканировать его карту |
| DELETE | `/api/v1/projects/files` | Удалить документ проекта и связанные временные workbook |

Связь карты с файлом — `Workbook.SourcePath` + `SourceSyncedAt`. Workbook
хранится JSON-блобом, миграция БД не нужна.

## Хранилище

`%APPDATA%\Gmind\markdown` (переопределяется `MARKDOWN_PATH`, `config.MarkdownPath`).
Открыть/сохранить можно любой абсолютный путь — бэкенд слушает только localhost;
относительный путь трактуется как путь внутри хранилища. Расширение обязано
быть `.md` / `.markdown`, иначе 400.

## Markdown внутри корня проекта

Модуль Markdown и дерево проекта решают разные задачи:

- `MarkdownPanel` работает с Markdown-хранилищем и произвольным открытием/
  сохранением файла;
- `ProjectTree` работает только внутри уже открытого корня проекта и сохраняет
  этот корень как навигационный контекст.

Создание из дерева:

1. UI передаёт `root`, id корневого workbook, выбранную директорию и простое
   имя файла.
2. Backend канонизирует root/directory через `Abs` + `EvalSymlinks` и проверяет,
   что directory находится внутри root.
3. Если расширения нет, добавляется `.md`; разрешены только `.md` и
   `.markdown`.
4. Файл создаётся через `O_EXCL` и получает `# <имя>\n`.
5. Корневой workbook пересканируется, после чего UI открывает новый документ.

Удаление из дерева разрешено для `.md`, `.markdown`, `.xmind`, но только внутри
канонического root. После удаления схема пересканируется, а workbook, чей
`SourcePath` совпадает с удалённым файлом, удаляется. Если пересканирование
сломалось, backend восстанавливает файл из backup.

Никогда не объединяй этот CRUD с произвольными абсолютными путями
`markdown_files.go`: project endpoint обязан оставаться confined к связанному
корню. Полный UX-контракт: `wiki/18-project-root-navigation.md`.

## Гочи

- `callTRPCQuery`-подобной коэрции здесь нет: `limit`, `size` и прочее приходит
  строками — приводить явно.
- Пустые значения свойств (`""`, `0`, `false`, `[]`) не пишутся в
  `<!-- gmind: … -->`, иначе файл зарастает шумом (`compactMeta` / `Meta.isEmpty`).
- `importTopicTree` (frontend) создаёт узел заголовком, а тело/заметку/свойства
  досылает вторым запросом — `createTopic` принимает только заголовок.
- После create/delete обязательно возвращай обновлённый корневой workbook:
  Sidebar строит дерево из его `root_topic`, а не сканирует диск самостоятельно.
