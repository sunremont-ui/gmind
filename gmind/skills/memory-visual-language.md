# Визуальный язык: корпуса памяти и раскладки

Gmind — место, где память видно и можно править руками. Чтобы карта читалась с
одного взгляда, у каждого вида памяти есть свой **корпус** (узнаваемый силуэт
узла), а у ветвлений — **выводы**. Аналогия из электроники прямая: деталь
узнают по корпусу, не читая маркировку.

## 1. Корпуса — `frontend/src/renderer/memoryPackages.ts`

Корпус = форма + цвет + тип обводки + насыщенность заливки + короткий код.

| Код | Вид | Форма | Почему такая |
|---|---|---|---|
| WRK | working | `note` | Черновик с загнутым углом; пунктир + прозрачная заливка — живёт недолго |
| EPS | episodic | `parallelogram` | Скос читается как движение по времени |
| SEM | semantic | `rounded` | Базовый спокойный корпус устойчивого знания |
| PRC | procedural | `hexagon` | Корпус-гайка — деталь механизма |
| ART | artifact | `rectangle` | Коробка; плотная заливка = готовый результат |
| MET | meta | `ellipse` | «Мысль»; двойная обводка — уровень над остальными |
| CNV | conversation | `pill` | Капсула-реплика |
| ENT·P/L/O/C | person/place/org/concept | `rounded` | Наследуют корпус semantic, различаются кодом и иконкой |
| PRC·S | skill | `hexagon` | Наследует procedural |
| ART·R | result | `rectangle` | Наследует artifact |
| MET·D | decision | `diamond` | Ромб блок-схемы = развилка |

### Приоритет оформления

```
явная настройка узла  →  корпус вида памяти  →  тема
```

`resolveNodeSkin()` сводит их в одно оформление. Поэтому смена `memory_kind`
никогда не затирает то, что человек настроил руками — свобода за пользователем.
Исключение: выделение и drop-target перебивают цвет корпуса (кроме случая, когда
цвет рамки задан явно) — обратная связь взаимодействия важнее.

### Расширяемый реестр

Корпуса — данные, а не константа. Пользователь добавляет свои виды и
переопределяет встроенные прямо в таблице:

- `BUILTIN_PACKAGES` — то, что описано в коде;
- `setCustomPackages(list)` — «внедрение» пользовательских корпусов. Вызывает
  `store/memoryPackages.ts` (Zustand + persist в localStorage);
- `allPackages()` — встроенные + свои, с учётом переопределений (дублей нет);
- `isOverridden(kind)` / `builtinPackage(kind)` — для метки «изменён» и сброса;
- `validatePackage(pkg, shapes)` — проверка перед сохранением.

Реестр остаётся **чистым и синхронным**: данные приходят снаружи, поэтому
`memoryPackage()` и `resolveNodeSkin()` можно звать из рендера узла и покрывать
тестами без React. Тот же приём, что `RegisterTool` на бэкенде.

⚠️ `store/memoryPackages.ts` импортируется в `App.tsx` намеренно: при
восстановлении из localStorage стор наполняет реестр. Без этого импорта свои
корпуса появлялись бы только после открытия Memory Workbench.

## 2. Роль узла: ветвление или лист

`nodeRole(childCount, isRoot)` → `leaf` | `branch` | `hub` (корень или ≥5 детей).

`NodePins.tsx` рисует короткие штрихи на тех сторонах, куда уходят дети — по
силуэту сразу видно, ветвление это или простой узел. У листа выводов нет.
Свёрнутая сторона даёт бледные выводы: ветка есть, но скрыта. Больше 5 штрихов
на сторону не рисуем — сливаются в гребёнку. Хаб получает более крепкую обводку
(`strokeScale`), но заданную вручную толщину рамки роль не трогает.

## 3. Таблица корпусов — Memory Workbench → таб «📦 Корпуса»

`components/MemoryWorkbench/MemoryPackageTable.tsx` — три роли в одном:

1. **Документация**: миниатюра (тем же `shapePath`, что и настоящий узел), код,
   ключ, форма, обводка, заливка, слой, подсказка «где применяется».
2. **Пикер**: клик по строке ставит `memory_kind` выделенному узлу (локально
   сразу + `api.updateTopic`).
3. **Редактор**: «+ Добавить корпус», правка (✎) и удаление (🗑). У встроенного
   вида ✎ создаёт переопределение, ↺ возвращает исходный корпус.

Таб не зависит от связи с MASys — это визуальный язык самого Gmind.

## 4. Раскладки вокруг узла — `frontend/src/renderer/radialLayout.ts`

Пять способов разделить 360° вокруг узла:

| Вид | Поведение |
|---|---|
| `radial-even` | Круг делится нацело на число детей — строгая симметрия |
| `radial-packed` | Сектор пропорционален габариту ветки — компактно, без пустот |
| `radial-rings` | Что не влезло в кольцо, уходит на следующее (шахматкой) |
| `radial-clock` | Фиксированные 12 позиций циферблата |
| `radial-sector` | Веер 180° вправо |

`radial` — историческое имя, ведёт себя как `radial-even`.

### Почему узлы не закрывают друг друга

Каждому поддереву сопоставляется описанная окружность радиуса
`r = hypot(w, h) / 2` вокруг его центра. Если описанные окружности соседей не
пересекаются, не пересекаются и габариты — **при любом угле поворота**. Угловой
полураствор ребёнка на расстоянии `R` равен `asin((r + gap/2) / R)`; сумма
секторов монотонно убывает по `R`, поэтому радиус подбирается двоичным поиском
(`fitRadius`). Наложений не возникает по построению, а не «вычищается» потом.

Прежняя реализация ставила детей по 8 фиксированным направлениям и надеялась на
общий проход `resolveOverlaps` — тот проход остался страховкой для остальных
раскладок.

**Гоча межкольцевого шага:** центры на радиусах `R1` и `R2` удалены минимум на
`|R2 − R1|`, поэтому шаг обязан покрывать габарит и крупнейшего в текущем
кольце, и крупнейшего среди ещё не размещённых (`ringStep`). Иначе большой узел
на внешнем кольце садится на маленький с внутреннего — ошибка, найденная тестом
на детей разного размера.

### Тесты

`radialLayout.test.ts` проверяет главное требование напрямую: для каждого из 5
видов — попарное отсутствие наложений bbox поддеревьев при 1…40 детях, на
разнородных размерах, с потомками и при нулевом зазоре. Плюс геометрия:
равноудалённость и равные углы для `even`, правая полуплоскость для `sector`,
несколько радиусов для `rings`, кратность шагу для `clock`, компактность
`packed` против `even`, сохранение внутренней раскладки поддерева при переносе.

### Где выбирается

- `PropertiesPanel` → «Layout» (с подсказкой под списком для радиальных видов);
- контекстное меню узла на холсте — пункты из `RADIAL_KINDS`.

Раскладка задаётся на узле (`Topic.structure_class`), поэтому в одной карте
разные ветки могут иметь разные виды.
